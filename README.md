# BNB Treasury Bot

维护 USDⓈ-M Futures 的 BNB 库存。策略规则见 [DESIGN.md](DESIGN.md)，默认配置见 [config/strategy.toml](config/strategy.toml)。纯决策与交易所执行分离，写请求先落 SQLite 意图；UNKNOWN 买单和划转不自动重发，已核验订单的撤单按受控退避恢复，已知成交也必须等余额覆盖后才能继续。

## 安装与检查

需要 Python 3.11+。项目使用 `.venv/bin/python`；Binance 接入采用[官方模块化 SDK](https://github.com/binance/binance-connector-python)，固定版本见 `requirements.txt`。

```bash
uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/python -m pytest -q
.venv/bin/python -m services.cli --help
```

测试通过模拟交易所和官方 SDK 的模拟 HTTP/WebSocket 传输运行，不需要凭据，不发真实订单、划转或通知。测试环境需要 pytest。

## Paper 模拟交易

Paper 使用币安公开现货行情和独立虚拟账户，不需要 API Key。订单、资金、成交和流水保存在 SQLite，原有策略、划转风控、预算、对账和 UNKNOWN 恢复逻辑继续执行。

```bash
.venv/bin/python -m services.cli --paper
.venv/bin/python -m services.cli --paper --status
```

默认数据库为 `var/paper.sqlite3`，参数见 [config/paper.toml](config/paper.toml)。`--paper-config PATH` 指定模拟参数，`--db PATH` 指定执行库；`--paper` 与 `--live` 互斥。新库原子生成账户、身份与现货基线，已有库恢复原状态，不重新注资。模拟参数、划转最小量和模型版本绑定数据库，修改后须选择新库；真实账户与 paper 不能共用执行库。首版要求 `spot_activity_symbols` 为空。

默认合约为 100,000 USDT 和 24 BNB，现货为 0 USDT 和 0.5 BNB。模拟 BUY 费用统一为 0.1%，从买入的 BNB 扣除；每个实际用于模拟推进的新源时间盘口报价提供卖一数量的 10% 作为全部订单共享的成交额度。盘口由公开 REST 深度快照和连续 diff 更新重建，断流或序列缺口后重新预热。支持 Maker、LIMIT GTC 和 IOC，含部分成交；挂出的订单由后续报价驱动，按限价成交。此模型不还原盘口排队或真实成交率。手续费预留仍须覆盖配置费率，默认 24h 划入预算仍为 3,000，不会因模拟模式放宽。

支持稳定币双向划转及 BNB 现货回划合约。受理后预留源资产，默认等待 2 秒模拟运行时间，再原子结算两侧余额并生成合约收入。合约 BNB 默认按 0.04 BNB/小时消耗，每累计一分钟结算；设为 0 可关闭。停机期间不补造成交、不补扣消耗，重启后划转继续等待剩余时间。进程仍运行时，`--mode PAUSED` 禁止新订单与划转，存量成交、已受理划转和消耗仍可发生。正常重启不传 `--mode`，保留原暂停状态。

paper 使用简化的无持仓合约模型：稳定币余额为模拟保证金，BNB 为手续费库存，`maxWithdrawAmount` 等于稳定币余额减配置不可划出额度及未结算调出资金，不能以 `availableBalance` 替代。它不模拟合约盈亏、资金费或强平，也不能验证真实账户权限、专属过滤器、费用或保证金安全性。

启动、重启和真实断流后仍须积累完整 15 分钟行情窗口才允许新买单。`--once` 只推进和检查一次，不跳过预热。`--status` 以只读连接查看原始已提交状态，不启动行情、不推进模拟，也不创建不存在的库。状态增加虚拟余额、冻结量、活动订单、最近 20 笔划转流水及费用/消耗累计值。告警只写带 `PAPER` 标记的日志，忽略生产密钥及 Webhook 配置。

划转回执丢失且未取得 `tranId` 时，仍保留 UNKNOWN。检查 `--status` 中的模拟划转流水，停止控制器后使用下文的绑定命令，并加上 `--paper` 和相同 `--db`；查询不到或相同金额不能自动解除。已确认操作仍须通过现货及合约余额对账，不提供重置余额或清除 UNKNOWN 的命令。

## 运行与暂停

通过 `BINANCE_API_KEY`、`BINANCE_API_SECRET` 提供凭据，密钥不写入配置。目标账户需要现货读取/交易及通用划转权限，系统时钟须同步。

首次使用新库或升级后缺少基线时，先停止其他程序及人工现货活动，确认旧成交和划转已全部结算，取消已声明交易对的外部活动订单，并保存一致备份。再显式初始化一次：

```bash
.venv/bin/python -m services.cli --db var/treasury.sqlite3 \
  --initialize-spot-baseline --operator operator-name \
  --reason '外部资产活动已停止，旧成交及划转均已结算'
```

命令只读交易所，核对账户和历史后保存首个基线。它拒绝活动意图、冻结资产、观察到的并发交易及已有检查点，不能用于清除差额。两次余额相同不能替代静默前提；无法暂停共享现货活动时不能采用这一初始化方式。已有可信基线无需重建。缺少基线时，普通启动保持门禁并告警。

只读取账户、保存状态并生成计划：

```bash
.venv/bin/python -m services.cli --db var/treasury.sqlite3 --once
```

去掉 `--once` 持续观察；观察模式不提交撤单。确认目标账户和权限后启用实盘：

```bash
.venv/bin/python -m services.cli --db var/treasury.sqlite3 --live --mode AUTO
```

一个账户只使用一个执行数据库。数据库绑定认证账户 UID 的哈希、环境、策略及交易对；更换身份不能复用旧库。所有控制器（包括观察模式）和维护命令持有生命周期租约，第二个写进程直接拒绝；不同数据库或机器无法用此锁互相协调。`--status` 可以与运行中的控制器并行使用。

`--mode` 是启动参数，修改模式、绑定流水或导入证据前应先停止已有控制器。后续正常重启不传 `--mode`，保留暂停状态。`--mode PAUSED` 禁止新增买单和划转；启用 `--live` 时仍执行必要的保护性撤单。PAUSED 和退出都不会保证撤销全部 GTC，停机后存量单仍可能成交；本程序没有全部撤单后停机命令。

冷启动或行情断流后重新积累完整 15 分钟窗口，这期间包括 URGENT 在内的新买单都被禁止，已有可确认 BNB 的回划和订单保护使用各自门禁。失败读取采用持久化退避；429/418 尊重 Retry-After，模式重置及重启不能跳过等待。

`--min-transfer-bnb/usd` 覆盖内部划转最小量，须有限且非负。配置费用预留必须覆盖完整 BUY commission，IOC 缓冲不得超过 1%。资产支持还取决于目标合约账户是否为该稳定币提供资产级 `maxWithdrawAmount`；`availableBalance` 不能替代它，最小划转粒度硬 veto 不因 URGENT 放松。

## UNKNOWN 与余额结算恢复

```bash
.venv/bin/python -m services.cli --db var/treasury.sqlite3 --status
```

状态包含未决请求、撤单尝试及截止时间、现货与合约结算差额、启动传输退避、相关操作、账户绑定、数据库/WAL 大小、剩余磁盘、告警积压和最老未决时间。

订单用客户端 ID 或已经核验的交易所 ID 查询。撤单 PENDING/UNKNOWN 可以恢复：必须先查到原绑定订单仍为 NEW/PARTIALLY_FILLED，核验归属，并遵守持久化退避及 Retry-After；同一意图最多发送 5 次，逐次审计。查询不到或查询失败不构成再次撤单或释放余额的证据。达到上限会发出 CANCEL_RECOVERY_EXHAUSTED；在交易所核查并撤销该订单后，正常对账继续确认成交和余额，不能删除撤单记录来重试。通用划转没有客户端幂等参数；未取得 tranId 的超时始终阻断，余额增加、一次查询不到或等得足够久都不是归属/失败证明。取得明确交易所流水后，停止控制器并执行：

```bash
.venv/bin/python -m services.cli --db var/treasury.sqlite3 \
  --bind-transfer-id LOCAL_CLIENT_ID EXCHANGE_TRANSFER_ID
```

命令只核验未决划转的资产、金额、方向、终态及唯一归属，保存结果后退出，不提交交易。CONFIRMED 后还须等待现货和合约余额完成核对。完整划转回执和操作结果原子落库，旧的 CONFIRMED 未结算操作也可自动补证据。没有可核验流水的 UNKNOWN 需继续保留并升级人工核查；不能删除日志、清空数据库或盲重发。

现货结算以一个持久化余额基线加去重资产事件核对 BNB 和 quote 两种资产，涵盖买入、卖出、真实 quoteQty、手续费和现货/合约划转。即使订单已全成或撤销，任何一侧余额滞后都不能制造新补货缺口。

恢复历史跟随可信检查点和最早未结算意图，不受 24h 预算或原 49h 回查窗口限制。合约结算必须由真实收入流水解释手续费、已实现盈亏、资金费及划转；不以任意资产更新时间或单向余额变化代替证据。合约收入与通用划转的 tranId 不直接互认；缺回执、矛盾记录或时间边界不明确时保持阻断，`--status` 显示原因。所需证据超过交易所保留期（收入三个月；通用划转采用保守的 180 天上限）时停止自动恢复。保留数据库和状态，取得交易所归档证据并通过经验证的来源适配恢复，不能清库、任意补差额或重置基线。

共享账户的其他交易对须在 `exchange.spot_activity_symbols` 声明，例如 `["ETHUSDT", "ETHBTC"]`；在其他交易对支付 BNB 手续费也需要读取该交易对。已声明交易对发生回执迟到时，结算失败会冻结检索水位并自动从检查点补查，重启后仍有效。若此前漏配，状态会保留差额。停止控制器后可以从认证接口补取缺失成交：

```bash
.venv/bin/python -m services.cli --db var/treasury.sqlite3 \
  --import-spot-trades ETHUSDT ETHBTC \
  --operator operator-name --reason '核对共享账户成交及 BNB 手续费'
```

工具保存操作员、原因、真实回执引用和基线前后状态，重新对账后输出剩余差额；重复导入不会重复入账。不接受任意金额覆盖，不解除 UNKNOWN 身份，不提交交易。修正配置后再启动控制器。

充值、提币、理财、兑换、奖励等外部变化在空闲时可随有效库存接受；与开放本机订单或未决划转重叠而造成差额时，仍需补齐必要证据。严格窗口中不能用成交导入伪造现金流、重置余额或清除未决责任。

## 升级与数据维护

升级前停止旧控制器并用 SQLite backup 保存一致备份，保留同一数据库及 WAL。schema 2 的已有账户不需要换库或重新初始化；缺失的新代次字段按 0 兼容读取。空闲旧库在新的有效账户/订单/预算观察后可以接受外部变化；仍开放的本机 GTC、部分成交、UNKNOWN、待结算划转和撤单继续使用原身份与基线恢复，升级本身不证明操作成功。缺必要基线或划转身份时保留阻断，继续使用原证据导入和人工绑定入口，不能用新余额补成成功。

活动/未决操作、订单、成交时间及 outbox 使用索引，空成交批次不扫描历史保护事件。历史流水不自动删除；安排备份与 WAL checkpoint，保留幂等身份和未决证据。数据库写失败会写 stderr 并停止新增执行，部署应配外部进程监督，并独立设置指数重启退避与启动失败告警。认证和维护错误也保存退避并写日志，账户身份验证失败不会提前绑定业务账本。

## 告警与策略边界

默认日志告警；设置 `ALERT_WEBHOOK_URL` 后投递至 HTTPS 接收端，接收端须支持 `Idempotency-Key`。outbox 使用独立数据库连接，慢账户读取不阻塞投递；失败记录及逐渠道送达状态保留。磁盘不足、WAL 增长、消息积压和长时间未决均有告警。

冻结 BNB 和外部买单仍计入经济总敞口，但不能当作立即可回划库存。合约紧急且库存受限时发出 `INVENTORY_UNAVAILABLE`，需协调冻结/外部订单，不忽略它们额外加买。

24h 预算限制合约向现货的稳定币调入，并不限制全部买入支出；现货原有资金仍可在其他门禁允许时使用。完整资金申请若违反比例或绝对下限，保持 veto，不自动改成更小申请。成交毛数量限制保护事件买入额度，实际净余额决定库存。

合约盈亏金额不下调 BNB 补货目标；普通目标使用配置的 `b_target`（默认 32），急跌保护下的紧急目标仍按原规则限制。空闲时采用当前有效库存，不要求解释外部资金来源；本机订单/划转责任窗口内继续核对成交、收入及双边余额，必要证据缺失或不一致仍阻断新增动作。在线路径不再计算历史消耗率及保证金变化指标。旧配置的 `margin_drop_limit`、`margin_target_reduction` 兼容读取，但不再影响策略。

离线回归不能替代目标账户的权限、收费、资产支持、共享限流和生产网络验证。保护性撤单会在历史读取前及读取之间优先执行，但正在进行的一次同步 SDK 请求仍可能延迟响应；实际延迟可通过保护与撤单事件时间测量。

### 固定库存阈值

补仓紧迫度使用当前有效的合约 BNB 库存，默认下限/预警/目标/上限为 25/28/32/40 BNB；历史消耗率不再触发提前紧急升级。已有补仓轮次、连续确认、URGENT 退出缓冲和收尾容差保持，未决操作及结算等待仍阻断新增动作。旧预测字段仅兼容读取，新决策不报告预测耗尽时间。

`--status` 对实盘和 paper 都使用只读连接，不连接交易所、不创建不存在的库或推进状态。`reconciliation.observation_mode` 区分空闲观察、严格窗口和未初始化；`responsibilities` 列出开放/未决操作身份、原基线、代次及缺失恢复证据，`observation`、`spot_settlement`、`futures_settlement` 分别说明数据或结算阻断。`accepted_inventory` 是库存接受记录，不代表其中某笔操作已被证明覆盖。旧历史诊断可保留展示，但不再单独阻止空闲库存。

阶段一仍可能在开放 GTC 期间被外部活动阻断；不会为接受外部余额自动撤销正常订单。预算、急跌累计、切片截止时间、续作和退避均保留，不能清库或盲重发。

历史读取现在按操作责任决定范围。空闲且无资金占用证明需求时，不查外部交易对成交或合约收入；已有本机订单历史时，仅保留本交易对最近 60 秒的迟到回执观察。开放 GTC 和待结算操作从原基线继续完整核对，超过 72h 不截断；必要证据超过交易所保留期仍等待认证归档恢复。预算始终读取账户级滚动 24h 划转，已知相关外部在途不会因一次查询缺席而消失。
