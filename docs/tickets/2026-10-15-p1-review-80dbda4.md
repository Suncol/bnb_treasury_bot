## P1-01：本地未发送请求不能形成 UNKNOWN 操作

**问题与影响。** 第一次限流预检通过后，后台公共请求可能更新共享额度；第二次预检在 SDK 写调用之前抛出 `RequestDeferred`。执行器把它当成可能已发送，永久等待不存在的操作。真实模块验证：网络写入 0 次、未决 UNKNOWN 1 条、`api_errors=1`、`failure_recorded=True`，订单的资金续作资格被消耗。

**定位。** [executor.py](../../services/executor.py):85、146、204–278；[sdk_transport.py](../../services/sdk_transport.py):134–149；[exchange_adapter.py](../../services/exchange_adapter.py) 的错误边界。

**修复范围。** 在最靠近发送的传输边界区分确定未发送、明确拒绝、可能已发送。仅从未发送过的新意图可保存可审计的未发送终态/原因，原子恢复此前续作资格并释放其结算门禁。既有 PENDING/UNKNOWN 撤单的本次恢复尝试未发送，只更新冷却及尝试记录，不改变旧操作状态、原有门禁、敞口或续作资格。两种本地未发送均不累计 API/划转失败，不消耗实际撤单发送次数。保留冷却和已持久化切片截止时间。不得仅靠异常名称推断发送状态，也不得把崩溃后没有回执的旧意图推定为未发送。

**验收条件。**

- 在首次预检通过、意图持久化之后、SDK 写调用之前注入额度耗尽；覆盖买单、USD 调入、BNB 回划、USD 回扫及撤单，HTTP 写入数均为 0。
- 操作、续作资格、失败计数和冷却在同一结果事务内保持一致；结果事务失败及重启仍不会误发或丢失原身份。
- 冷却到期后先对账和重新规划；不在同轮立即重试，不回退切片等待时间。
- 真正的超时、响应丢失、5xx、解码失败、已发送的 429/418 仍 UNKNOWN；重启不重复发送。
- 撤单未发送时不耗尽最多 5 次的真实发送机会；此前已经发送过且结果未知的撤单继续保留原身份和未知敞口。

**测试与文档。** 扩展 `test_binance_sdk.py`、`test_execution_boundaries.py`、`test_review_recovery.py`；更新 DESIGN 11.3、14.2、14.3。现有测试只覆盖首次预检已限流，必须增加两次预检之间的竞态。

## P1-03：资金被外部占用后结束旧续作，让下一库存周期重新评估

**问题与影响。** `resume_replenishment` 禁止再次调资，但仍有缺口时一直保留。完整复现：合约 27 BNB，先调入 3000 USD；外部 BTCUSDT 成交耗用这笔资金，经原成交导入和对账确认；25h 后预算释放，再经过两个各 30 分钟的库存周期，AUTO、数据有效、无未决、缺口 5 BNB、现货 USD 为 0，仍只存在最初一次划转。

**定位。** [runner.py](../../services/runner.py):657–660、797–825；[executor.py](../../services/executor.py):139–149。DESIGN 9.2、14.4 明确限制本次续作再次调资，不能简单删除该限制。

**已确认决定。** 外部现货交易的真实支出或冻结已经核验，且占用使旧续作无法完成最小可执行买单时，结束旧资金续作。仅下一个有效库存周期可以重新申请资金；同一次续作及同一调度轮不得追加调资。见 [ADR-0002](../adr/0002-funded-continuation-exhaustion.md)。

**修复范围。** 将资金占用与临时门禁分别判断。占用判断须有外部成交/活动订单及余额证据，不能仅凭现货自由余额变小。若剩余资金仍支持合规缩量订单，继续按余额预算。退出与下一次资格持久化，重启不提前获得资格；复用已有调度状态，只有无法表达时才增加必要持久字段并明确迁移。

**验收条件。**

- 完整 Runner 场景分别覆盖已确认支出、已核验外部冻结；旧续作终止后，非库存行情/对账 tick 和本轮不调资，下一个有效库存周期才按全套风控申请。
- 对外部冻结，核对相关订单归属、资金冻结和整体 BNB 敞口；本策略自身冻结不能误认为外部占用。
- 仅涨价、资金仍能缩量买入、切片等待、追价限制、行情失效、PAUSED 不触发资金占用退出。
- UNKNOWN、未结算或无法解释的差额继续阻断，不能为恢复调资提前清除。
- 占用证据、退出、下一库存周期之间插入重启和提交失败，不重复划转；预算耗尽和粒度硬 veto 仍禁止调资。

**测试与文档。** 扩展 `test_replenishment_continuation.py`、`test_execution_boundaries.py` 和共享账户对账测试；更新 DESIGN 7.6、9.2、14.2、14.4；保留旧续作数据兼容性。

## P1-04：正常账户观察不一致不累计 API 故障

**问题与影响。** `/fapi/v3/balance` 与 `/fapi/v3/account` 顺序读取间正常成交会使钱包或版本不同。两次读取均成功，却被抛为通用 ExchangeError，Runner 累计 API 错误。三次注入结果为 AUTO、AUTO、PAUSED；后续数据恢复也需人工解除暂停。

**定位。** [binance_adapter.py](../../services/binance_adapter.py):104–122；[runner.py](../../services/runner.py):222–289；[executor.py](../../services/executor.py):302 起。

**已确认决定。** 将读取成功但账户观察不一致作为可恢复数据状态，持续有界重读并告警，不计入 API 三连失败，也不单独造成持久化 PAUSED。真实 API 连续三次、划转连续两次失败的既有暂停政策保留；不一致期间冻结新增动作并继续必要的保护性撤单。

**修复范围。** 建立明确的数据不一致结果/异常类型，避免靠错误字符串分类。丢弃混合快照，不复用旧缓存，不推进库存状态、确认计数、切片或成功库存时间。重读服从现有调度、预算与退避，避免循环忙等；持续不一致沿用有节制的诊断/告警。

**验收条件。**

- 用模拟 SDK 在两次账户读取之间改变余额/版本，连续三次不一致仍为 AUTO、没有新增订单/划转；之后一致数据到来可自动恢复正常周期。
- 保留此前真实 API 失败的计数，不因一次数据不一致清零；数据不一致自身不增加计数。
- 网络错误、认证失败、429/418、真正未知写结果继续使用原错误边界及持久化冷却；不要把真实错误包成数据不一致。
- 失效观察不推进业务状态、快照历史和结算水位，保护性撤单仍遵守身份、模式和服务端禁用窗口。

**测试与文档。** 新增 SDK→Runner 的完整观察竞态测试；覆盖 `test_state_machine_gates.py`、`test_audit_availability.py`；更新 DESIGN 5.2、11.3、14.3。与 P1-07 共用账户一致性分类。

## P1-05：限制整段收入复查的触发范围，并避免慢审计耗尽账户有效期

**问题与影响。** `_inputs()` 使用 `inventory or execute_enabled` 强制审计，使启用执行的每次维护对账都成为全量扫描。完整离线验证：24h 基线、库存 32 BNB、三次间隔 10 秒的非库存维护周期，无任何写请求，却三次查询相同的 86401.001 秒区间。用户定义的 P1 场景还包括大流水导致慢审计和持续过期，实施时须补充这一性能复现。

**定位。** [runner.py](../../services/runner.py):562–625、630–679；[reconciliation.py](../../services/reconciliation.py):388–393、`_refresh_income()`、`audit_income()`；[executor.py](../../services/executor.py):43–54。

**已确认决定。** 将收入区间完成审计的证据与当前账户快照的新鲜度分开验证。每个新库存/执行批次仍须整段审计；慢扫描后重读新鲜一致账户、补齐新版本区间并重新核对余额，再授予该批次执行资格。旧账户不续期，也不以五分钟覆盖缓存替代新批次整段审计。见 [ADR-0003](../adr/0003-income-audit-and-account-freshness.md)。

**修复范围。** 区分纯维护观察与新的库存/执行批次。纯维护复用既有 5 分钟有限覆盖缓存；真正推进库存决策或提交新意图前，仍完成所需区间整段复查和余额核验。记录审计区间及扫描完成证据，随后按最新账户资产版本补齐增量并重新验证；不能只把原审计时间改成当前时间来伪造新资格。有效执行资格只属于当前批次，并受最终已核验账户的原 10 秒有效期约束。批次结束、重启、证明失败或保护性撤单使观察失效后重新取得资格。分页及慢读取期间保留已有风险检查边界；不因重读新账户而无限重开相同整段扫描。

**不可删减的安全要求。** DESIGN 11.2 已明确收入 API 没有完结水位，新执行批次必须整段审计；五分钟缓存不能替代该要求。晚到的相互抵消资本/亏损、重启、UTC 回退、覆盖失效及失败事务仍须被发现或保持阻断。实施时必须同步改写现有“审计资格绑定原账户时间”的条款，保留最终账户有效期和新版本收入核对；不得同时保留互相矛盾的两套有效期规则。

**验收条件。**

- 无动作维护连续运行，覆盖缓存有效且资产版本不变时不重复查整段；过期、时钟回退、缺复查时间时重新查整段。
- 真正库存周期或从维护转入写执行前，整段审计成功才允许状态推进和新增意图；资格及覆盖有效时，同批次相同需求不重复整段读取；重启、UTC 回退、证明失败或保护性撤单使观察失效时不得沿用。
- 构造多页大流水和可控读取延迟（含一次整段审计超过账户 10 秒有效期）：在扫描后账户读取及必要增量可以于账户有效期内完成的夹具中，通过新鲜一致账户恢复可执行状态，避免持续重复全段而无进展。若后续读取也持续超时，仍须阻断，不能以进展要求放宽门禁。
- 慢审计期间急跌风险仍能在既有读取边界处理；不新增无限任务队列，不延长账户/行情寿命，不把慢查询当作成功证据。
- 查询、分页或入库失败不推进覆盖；迟到收入、unsupported capital、UNKNOWN、跨重启和分页重复的现有安全回归全部保留。
- 记录同一夹具修复前后的整段/增量请求次数、页数、快照年龄和是否最终产生合法计划。用虚拟时钟断言行为，不用本机毫秒阈值冒充生产 SLA。

**测试与文档。** 扩展 `test_margin_history.py`、`test_refresh_schedule.py`、`test_audit_availability.py`，增加大流水慢审计集成场景；更新 DESIGN 11.2、13、14.5。保护撤单和新财务写操作的审计要求分别验证。

## P1-06：用连续本地订单簿替换双深度流末编号关联

**问题与影响。** `DepthSnapshots` 只在 partial 的 `lastUpdateId` 等于 diff 的 `u` 时生成报价。相同编号对照产生 60 个报价，持续错位对照产生 0 个报价；行情线程按成功报价静默触发重连，窗口反复清空。官方定义两类流的字段，但没有一一对应末编号保证。

**定位。** [market_depth.py](../../services/market_depth.py):19–65；[market_stream.py](../../services/market_stream.py):64、118、162–184。

**已确认决定。** 使用官方 REST 深度快照初始化，缓冲并连续应用 diff depth；从重建后的完整已知盘口取得买一、卖一及卖一数量，将报价归属到已应用事件的源时间。见 [ADR-0001](../adr/0001-local-depth-book.md) 和 [官方本地订单簿流程](https://github.com/binance/binance-spot-api-docs/blob/master/web-socket-streams.md#how-to-manage-a-local-order-book-correctly)。

**修复范围。** 通过官方 SDK 读取公开深度，处理初始化、缓冲、序列衔接、价位新增/覆盖/删除和 gap 后重建。快照请求服从共享限流、冷却和有限重试；初始快照深度有限，已知有效档位不足时重建，不发布不确定的最优价。网络等待不持有阻塞风险消费的锁，重建缓存有界，关闭后迟到结果不能重新发布。

## P1-07：在提交边界复核划转风控，并拒绝已观测额度矛盾

**问题与影响。** 规划时通过门禁不代表执行时额度未变。另有可确定修复的缺口：Adapter 先读 balance，再读 account；后者的资产行也有 `maxWithdrawAmount`，但当前只比较钱包余额/版本，最终仍取较早 balance 值。原代码验证：先读 50000、后读 4000、钱包和版本相同；返回 50000 后申请 3000 被放行，按 4000 应触发粒度 HARD_VETO。[官方账户资产字段](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/account)支持核对两处资产级额度。

**定位。** [binance_adapter.py](../../services/binance_adapter.py):104–155；[runner.py](../../services/runner.py):710–749、831–835；[executor.py](../../services/executor.py):76–157；[risk_checks.py](../../core/risk_checks.py):30–147。

**已确认决定。** 两份响应的资产级额度矛盾则阻断并重读，不任取较高值，也不擅自改为另一种资产口径。提交前使用最新可验证的资产级 `maxWithdrawAmount` 重做全部限制。承认最终读取与交易所受理并非原子操作，外部活动仍可能改变额度；本 ticket 不宣称消除该窗口。

**修复范围。** 为合约→现货 USD 调入增加统一提交前复核，Runner 及直接 Executor 调用均不能绕过。复用唯一的 `evaluate_transfer_gate()`，检查最新额度、最小粒度、单次比例、前后绝对下限、已确认及未决预算、交易所最小量、模式与结算门禁。重新取得的账户必须纳入原有收入/余额验证；复核与落意图之间避免插入无关慢读取。风控已不允许或申请量需要重新规划时结束旧候选，不把预算裁剪/比例 veto 当成无条件重试机会。

**验收条件。**

- `balance.maxWithdrawAmount=50000`、随后 `account.assets[quote].maxWithdrawAmount=4000`，钱包/版本不变：不能生成可执行的高额度快照；无划转写请求。一致的后续观察可恢复。
- 规划后、提交前降低可划转额，使最小粒度、单次比例或划转后下限任一不满足，写请求为 0；URGENT 同样硬 veto。
- 规划后预算被已确认外部划转或未决预占耗用，提交边界不越过滚动预算。确保同一意图不会被预算重复计算。
- 新观察过期、未来、非法、收入/余额未覆盖或仍不一致时不提交；快照时间与来源不因提交准备而续期。
- 覆盖正常允许、再次复核 veto、复核后未发送、发送后超时及重启；未发送不遗留幽灵 UNKNOWN，真正已发送未知不补发。
- 验收报告明确测试注入边界：能拦截最终复核已取得并验证的风险证据所显示的变化，不承诺识别 API 尚未暴露或最后观察后发生的全部外部变化；账户隔离或交易所原子条件不在本轮范围。

**测试与文档。** 扩展 `test_binance_sdk.py`、`test_execution_boundaries.py`、`test_risk_checks.py` 和 `test_transfer_settlement.py`；更新 DESIGN 7.3、7.4、14.3、14.4。依赖 P1-01 未发送语义及 P1-04 数据不一致分类。
